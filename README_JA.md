# sail-worktree

Laravel Sail プロジェクトを `git worktree` で複数同時に動かすためのツールです。
ワークツリーごとに `.env` を生成し、ポート番号が衝突しないよう自動で割り当てます。

このツールの出力（使い方・メッセージ・警告・エラー）は英語です。海外の開発者も使えるようにするためで、この README は [README.md](README.md)（英語）の日本語訳です。

## インストール

```sh
go install github.com/uehatsu-info/sail-worktree@latest
```

または、リポジトリを clone してビルドします。

```sh
go build -o sail-worktree .
```

## 使い方

### 1. `sail-worktree init`（任意）

`init` を実行する必要はありません。`up`・`stop`・`rm` は、compose ファイルとそのポート変数を自分で見つけます（[プロジェクトディレクトリ](#プロジェクトディレクトリ)を参照）。`init` を使うのは、その一覧をファイルに固定したいときだけです。たとえば、検出で拾えないポート（long syntax の `published:` や、`include:` した compose ファイルのポート）があるときや、一覧を編集したいときです。

Laravel プロジェクトのディレクトリ（`artisan` と compose ファイルがある場所）かその下で実行します。compose ファイルの `- '${APP_PORT:-80}:80'` のようなホスト側のポート指定から `${APP_PORT:-80}` のようなポート変数を検出し、その隣に `.sail-worktree.json` を書きます。新しく作れば "created"、既存のファイルを置き換えれば "updated" と表示します。置き換えると、そのファイルを手で編集した内容は失われます。全ワークツリーで共有するならコミットし、検出に戻すなら削除してください。ファイルは検出より優先されるので、compose ファイルの変更を `up` が無視しているように見えるときは、`git status` で未追跡の `.sail-worktree.json` が残っていないか確認してください。

#### `.sail-worktree.json` ファイル

```json
{
  "compose": "compose.yaml",
  "port_vars": [
    { "name": "APP_PORT", "default": 80 },
    { "name": "VITE_PORT", "default": 5173 }
  ]
}
```

- `compose`: compose ファイル。プロジェクトディレクトリ内の相対パスで書きます（`rm` が `docker compose -f` に渡します）。
- `port_vars`: `up` がポートを割り当てる変数。`default` は、変数が未設定のときに compose ファイルが使うポートです。空きポートは `default` + 1 から探します。

このファイルは手で書いても構いません（たとえば検出で拾えないポートを足すため）。あとで `init` を実行すると、検出した内容で置き換わります。

### 2. `sail-worktree up [args...]`

作成済みのワークツリーの、プロジェクトディレクトリかその下で実行します。

```sh
git worktree add ../myapp-feature-x feature-x
cd ../myapp-feature-x
composer install
sail-worktree up -d
```

- compose ファイルとポート変数は、`.sail-worktree.json` があればそこから取ります。なければ、実行のたびに compose ファイルから検出します（数えるのは `'${APP_PORT:-80}:80'` のようなホスト側のポート指定だけなので、`environment:` の項目を書き換えることはありません）。ファイルがない場合、compose ファイルでポート変数を増減したブランチでは、次の `up` でそのポートが割り当てられるか解放されます。
- `.env` がなければメインワークツリーの `.env` をコピーします（なければ `.env.example`）。
- `vendor/bin/sail` がないときは何も書き込みません。
- 各ポート変数に空きポートを割り当てます。デフォルト値の +1 から探索し、メインワークツリー用にデフォルト値は空けておきます。
- 他のワークツリーの割り当て済みポートと、ホストで使用中のポートは避けます。
- `COMPOSE_PROJECT_NAME` を設定し、`APP_URL` のポートも更新します。
- `SESSION_COOKIE` を `<COMPOSE_PROJECT_NAME>-session` に設定します（既存の値は上書きします）。`localhost` はポートが違っても Cookie を共有するので、名前を分けないとワークツリー同士のログインが混ざります。
- `up` が `APP_URL` を更新し（上記）、`.env` に `SANCTUM_STATEFUL_DOMAINS` があるときは、新しい `APP_URL` の `host:port`（スキームの既定ポートならホストだけ）を末尾に追加し、`SANCTUM_STATEFUL_DOMAINS: added <エントリ>` と表示します。Laravel Sanctum が `APP_URL` を自動で加えるのはこの変数が未設定のときだけなので、追加しないとワークツリーで Cookie 認証が失敗します。
  - Sanctum の照合規則で一致するエントリが既にあるとき（ワイルドカードや `__SANCTUM_CURRENT_REQUEST_HOST__` も含む）、変数がないとき、値がステートフルドメインを無効にするとき（空、`null`・`false`・`true`・`empty`、`(null)` のように括弧で囲んだ同じ語、カンマだけ）は追加しません。
  - 単純なリストでない値（`${APP_URL}` のような変数、コメント、内側の引用符、引用符の外の空白など）や、単純なホスト名・IP アドレスでない `APP_URL` のホスト（ほかの文字、IPv6 のゾーン、IPv4 射影 IPv6 アドレス）は変更せず、追加すべき値を示す警告を出します。警告は `up` のたびに出ます。値が原因の警告は、値にそのエントリが独立した要素として入れば止まります（引用符の後ろにコメントのない引用符付きの値なら引用符の内側に、引用符のない値なら空白・タブ・`#`・引用符がまったくない形で、手で追加してください）。ホストが原因の警告は `APP_URL` を変えるまで続きます。
  - 既存のエントリは削除しません。古いポートのエントリは残り、ほかのポートのエントリ（Vite のポートなど）は更新しません。
- ポート変数と同名のシェル変数・`COMPOSE_*` の全て・`SAIL_FILES` は、`.env` より優先されてしまうので、`sail` に渡す環境（`stop` も同じ）と、`rm` の `docker compose` に渡す環境から外します。`DOCKER_HOST`・`DOCKER_CONTEXT` は意図して使う人がいるので外しません。
- 割り当て済みのポートは、次回以降も同じ値を再利用します。
- 最後に `vendor/bin/sail up <args>` を実行します。

### 3. `sail-worktree stop`

`sail stop` を実行します。

`stop` は何も拒否しません（`.env` を書き換えず、止めるのは取り返しがつくため）。代わりに、メイン以外のワークツリーで `.env`（通常ファイルのみ。リンクや FIFO は読みません）に `COMPOSE_FILE`・`COMPOSE_ENV_FILES`・`SAIL_FILES` があるとき、または `COMPOSE_PROJECT_NAME` がこのワークツリー用に再計算した名前と違うときに、別のプロジェクトを止める可能性があるので、stderr に警告を出します。警告はベストエフォートです（`.env` 内のシェル式や `.env.$APP_ENV` は検出できません）。メインワークツリーでは出しません。

### 4. `sail-worktree rm [-y]`

コンテナ・ネットワーク・ボリューム（DB データ含む）・ビルドイメージを削除し、割り当てたポートを解放します。
`docker compose --project-name <名前> --project-directory <プロジェクトディレクトリ> -f <compose> down -v --rmi local --remove-orphans` 相当です。確認プロンプトは `-y` で省略できます。
`.env` は削除しません。
取り返しがつかないので、`.env` の `COMPOSE_PROJECT_NAME` がこのワークツリー用に再計算した名前と一致しないとき（手で書き換えた・別のワークツリーの名前が残っている・ワークツリーを移動した）と、`.env` に `COMPOSE_FILE`・`COMPOSE_PROFILES`・`COMPOSE_ENV_FILES`・`SAIL_FILES` があるときは拒否します（`up` は `COMPOSE_PROFILES` を許しますが `rm` は許しません。`rm` の前にその行を消してください）。また、`compose` のファイルがリンクをたどった結果プロジェクトディレクトリ内の通常ファイルでないとき（プロジェクトディレクトリ外のファイルへのリンク、その外のディレクトリへのリンクなど）も `rm` は拒否します。これらの検査は全て確認プロンプトの前に行います。名前が一致しないときのエラーには復旧手順が出ます。通常は `.env` の `COMPOSE_PROJECT_NAME` を表示された名前（引用符なし）に戻してください。古い版が別の名前で作ったプロジェクトを消す場合だけ、手動の `docker compose -p <名前> down -v ...` を示します（名前が安全な文字種＝小文字英数字・`_`・`-` のときのみ。大文字を含む名前は compose が実際に使う名前と異なり得ます）。実行前に `docker compose ls -a` で、他のワークツリーやプロジェクトのものでなくこのワークツリーのものであることを確認してください。`up` が `COMPOSE_FILE` 等の行を拒否したときのエラーは、それがこのワークツリーの `.env`・メインワークツリーの `.env`・その `.env.example` のどれ由来かと、直し方を示します。

### 5. `sail-worktree version`

版を表示します（`go install ...@vX.Y.Z` ならタグ、手元の `go build` は `(devel)` か `v0.0.0-<日時>-<コミット>` の疑似バージョン）。プロジェクトでは `@latest` でなくタグを固定してください。

## プロジェクトディレクトリ

Laravel プロジェクトは、リポジトリのルートになくても構いません。どのコマンドも、カレントディレクトリから上にたどってプロジェクトディレクトリを探し、ワークツリーのルートで止まります。

1. ワークツリーのルートまでのどこかに `.sail-worktree.json` があれば、それがある最も近いディレクトリ
2. なければ、`artisan` と compose ファイル（`compose.yaml`・`compose.yml`・`docker-compose.yml`・`docker-compose.yaml` のうち最初に存在するもの）がある最も近いディレクトリ

`init` は、どちらかに当たる最も近いディレクトリに書きます。compose ファイルしかないディレクトリ（`.devcontainer/` など）には書きません。`vendor` と `node_modules` の下のディレクトリは飛ばします。`.sail-worktree.json`、または `artisan` の隣の compose ファイルが存在するのに通常ファイルでないときはエラーです。`.env`・`vendor/bin/sail`・compose ファイル・ポートの割り当ては、すべてプロジェクトディレクトリに属します。

```
myapp/                  <- ワークツリーのルート
|-- docs/
`-- laravel/            <- プロジェクトディレクトリ
    |-- artisan
    |-- compose.yaml
    `-- vendor/
```

```sh
cd myapp                                    # メインワークツリー
git worktree add -b feature-x ../myapp-feature-x
cd ../myapp-feature-x/laravel
composer install
sail-worktree up -d
```

- `.sail-worktree.json` を使う場合は、チェックアウトするブランチにそれが含まれている必要があります（そのコミットより前に作ったブランチにはないので、先にそのコミットをブランチにマージするか、ブランチをその上にリベースしてください）。
- 上の階層の `.sail-worktree.json` は、より近い Laravel プロジェクトより優先され、どのコマンドもそのことを警告します。近いアプリが無関係なら警告は無視して構いません。そのアプリを使うには、その中で `sail-worktree init` を実行してください（以後はそのアプリがプロジェクトになります）。
- メインワークツリーにも、同じ相対パスにプロジェクトが必要です。`up` は `<メインワークツリー>/laravel/.env`（なければ `.env.example`）から `.env` をコピーします。そのディレクトリはメインワークツリーの外に解決されてはいけません（シンボリックリンクはたどって確認します。Windows のジャンクションはたどりません）。確認するのはディレクトリだけです。そこにある `.env` 自体がリンクなら、ルートにあるプロジェクトと同じく、リンク先を読みます。
- ワークツリーの外に解決されるプロジェクトディレクトリはエラーです。compose の検査と同じく、これらの確認の後でリンクに差し替えられても検出できません。
- プロジェクトディレクトリより下（例: `laravel/app`）で `up`・`stop`・`rm` を実行すると、stderr に `project directory: "<パス>"` を表示します。
- プロジェクトディレクトリが見つからないときは、見つかるはずのサブディレクトリと、たどった途中で `artisan` だけ、または compose ファイルだけがあるディレクトリをエラーに示すので、ワークツリーのルートで実行しても行き先が分かります。
- プロジェクト名は `<メインワークツリー名>-<ワークツリー名>-<プロジェクトディレクトリのハッシュ>` です。ワークツリーのルートにあるプロジェクトでは、以前と同じ名前です。

## 補足

- `up` と `rm` はメインワークツリーでは実行できません。
- `.env` の安全: `up`・`rm` は、`.env` がシンボリックリンクのとき、または（Unix で）他のファイルとハードリンクされているときは拒否します（リンク越しにメインの `.env` を書き換えないため）。`up` は `COMPOSE_FILE`・`COMPOSE_ENV_FILES`・`SAIL_FILES` があるときも拒否します（あると compose が `up` の書くポートやプロジェクト名を読まなくなります）。`stop` はこの検査をしませんが、Sail は `.env`（`APP_ENV` があれば `.env.$APP_ENV`）をシェルとして `source` するので、シンボリックリンクの `.env` はこのツール経由でも `sail` を直接実行しても、リンク先がシェルとして実行されます。`.env` は信頼できる実ファイルにしてください。新規作成する `.env` は 0600、既存ファイルのモードは変えません（古い版が作った `.env` は自分で `chmod 600 .env` してください）。`up` が書くキーが複数行にあるときは、最初の行を残して残りを取り除くので、重複行で値が割れることはありません（Sail は最後の値、Laravel の Dotenv は最初の値を使います）。
- `.sail-worktree.json` の `compose` は、プロジェクトディレクトリ内の相対パスにしてください。これ（または検出した compose ファイル）を `rm` が `-f` に渡します。渡すのはこの 1 つだけなので、`rm` は `compose.override.yaml` を読みません。そこにしか定義されていないボリュームは残ります。`rm` は先にリンクをたどり、実体がプロジェクトディレクトリ外にあるファイルや通常ファイルでないものを拒否し、`-f` には実体のパスを渡します。この検査をするのは `rm` だけです。`up` と `stop` は、compose ファイルを自分で探して `-f` を渡さない `sail` を実行するためです。下の箇条書きも参照してください。
- 制限: Windows のジャンクションはたどらないので検出できません。`compose.yaml` という名前の壊れたリンクは飛ばすので、隣に `docker-compose.yml` があればそちらを使います。検査の後でリンクを差し替えられても検出できません。リンク経由の compose ファイルにある `include:` と `extends:` の相対パスは、リンク先のディレクトリを基準に解決されます。compose ファイルが参照するもの（`include:`・`extends:`・`env_file:`・ボリュームなど）は検査しません。
- compose ファイルがプロジェクトディレクトリ外のファイルへのハードリンクになっていても検出しません。これは意図した選択です。見分けられるのはリンク数だけで、そのリンク数は、意図してハードリンクで共有しているファイルも引っかけてしまうため、`rm` は `compose` についてこれを検査しません。通常のチェックアウトではハードリンクを作れません（git はハードリンクを保存しません）が、スクリプトや利用者は作れます。（`.env` は別です。`up`・`rm` はハードリンクの `.env` を拒否します。Unix のみ。`init` も同様に、シンボリックリンク越し、また Unix ではハードリンク越しには `.sail-worktree.json` を書きません。）
- `compose` のリンク、または `rm` が検出しないハードリンクを実ファイルのコピーに置き換えるときは、下の「リンクの `compose` ファイルの置き換え」の手順に従ってください。
- ポートは、全インターフェースと `127.0.0.1` の両方で束縛できるときだけ空きと判定します（`127.0.0.1` の権限エラーは macOS でのみ無視します。macOS は一般ユーザーが特権ポートに `127.0.0.1` を束縛することを許しませんが、Docker は束縛できるためです。`127.0.0.1` 自体が無い環境も空きとみなします）。1024 未満のポートは macOS では割り当て得ますが、Linux の一般ユーザーでは飛ばして 1024 から探します。Windows には `O_NOFOLLOW` がないので、シンボリックリンクの検査だけです。
- メインワークツリー自身の `.env` のポートはレジストリに載りません。探索はデフォルト値の +1 から始まるので、メインには +1 以外のポート（例: `APP_PORT=8080`）を割り当てるか、メインを先に起動してください。ポートの割り当てはロックしないので、複数の `up` を同時に実行しないでください。
- ポートの割り当て記録は `os.UserConfigDir()/sail-worktree/registry.json` に保存されます（macOS: `~/Library/Application Support/sail-worktree/registry.json`）。
- プロジェクトディレクトリには `vendor/bin/sail` が必要です（`composer install` 済みであること）。
- エラーメッセージでは、制御文字（レイアウトに使う改行を除く）・書式文字（双方向テキストの上書きなど）・不正なバイトをエスケープして表示します。細工したディレクトリ名で端末にエスケープシーケンスを送られることはありません（ただし、パスに含まれる改行の後ろは別の行として表示されます）。

### リンクの `compose` ファイルの置き換え

`compose` が、プロジェクトディレクトリ外に解決されるシンボリックリンク（`rm` は拒否します）か、その外のファイルへのハードリンク（`rm` は検出しません）のときに使います。プロジェクトディレクトリ内の通常ファイルを指すシンボリックリンクは、すでに `rm` の検査を通るので、この手順は要りません。リンクのパスに直接上書きコピーすると、リンク先のファイルも書き換わります。そこで、この手順は、新しい名前にコピーしてから、そのコピーをリンクの上に移します。

1つの Unix シェルで、プロジェクトディレクトリ（`.sail-worktree.json` または `artisan` がある場所）から実行してください。macOS の sh と zsh で試しました。Linux と Windows では試していません。

手順1の前に、ワークツリーに書き込むコンテナ、エディタ、ファイル監視を止めてください。

1. `.sail-worktree.json` の `compose` の値（または検出した compose ファイルの名前）を、引用符で囲んで変数に入れます: `f='compose.yaml'`。値に引用符（`'`）やバックスラッシュが含まれるときは、この手順を使わないでください（引用した変数が壊れます）。`..` を含めないでください。リンクがパスにあると、`rm` とシェルが `..` を別々に解釈するためです。`docs/../compose.yaml` のような値は、先に `compose` を `compose.yaml` のように `..` を含まないパスに直してください。
2. `ls -ldL -- "$f"` を実行します。先頭は `-`（通常ファイル）でなければなりません（例: `-rw-r--r-- 1 you staff ... compose.yaml`）。先頭が `-` 以外のとき、または `ls` が失敗したときは、ここで中止してください。リンクをプロジェクトディレクトリ内の通常ファイルに直すか、`compose` をそのようなファイルに変えてください。
3. `readlink -- "$f"` を実行します。シンボリックリンクのリンク先が表示されます（ハードリンクでは何も表示しません）。コピーは、その内容をワークツリーに持ち込みます。持ち込みたくないときは、ここで中止してください。
4. `compose` がサブディレクトリにあるときは、パスの各ディレクトリに、末尾にスラッシュを付けずに `ls -ld` をかけてください（`docs/sub/compose.yaml` なら `ls -ld -- docs docs/sub`）。`ls -ldL` はリンクをたどるので、パスの途中のリンクは、この方法でしか見えません。どれも先頭は `d` でなければなりません。それ以外のとき、または `ls` がエラーになったときは、いったん中止して、先にそのリンクを直してください。
5. `[ ! -e "$f.new" ] && [ ! -L "$f.new" ] && cp -- "$f" "$f.new" && mv -- "$f.new" "$f" || echo "not replaced: $f" >&2` を実行します。`$f.new` は一時的な名前で、まだ存在しない名前（リンクとしても存在しない名前）でなければなりません。`not replaced` と出たときは、何も置き換わっていません。`$f.new` を確認してください（元からあったか、移動されなかったコピーです）。消すときは `rm -- "$f.new"`、自分のファイルなら別の場所に移してから、同じ行をもう一度実行してください。
6. 何も出なくても、うまくいった証拠にはならないので、結果を確認します。`ls -l -- "$f"` の先頭は `-` で、権限の次の数字（リンク数）は 1 でなければなりません（ハードリンクが残っていると 2 以上になります）。`ls -l` は、パスの途中のディレクトリがリンクかどうかを示しません。サブディレクトリにあるファイルは、手順4のようにディレクトリをもう一度確認してください。
7. 相対の `include:`・`extends:`・`env_file:` のパスが意図した場所を指しているか確認してください。`rm` はこれらを検査しません（上の制限を参照）。コピーは新しいファイルなので、モードは元のモードと umask に従い、ACL と拡張属性はありません。必要なら設定し直してください。

確認とコピーは1つの操作ではないので、その間にワークツリーへ書き込むプロセスがあると、手順5がワークツリーの外に書き込むことがあります（`$f.new` として置かれたリンクや、確認のあとでリンクに差し替えられたパスの途中のディレクトリ）。先にプロセスを止めても、危険は下がりますが、なくなりません。ほかのツール、git の操作、ほかのユーザーも書き込めるためです。この方法で上書きされた外のファイルは、これらの確認では跡が見つかりません。

## アップグレード

### v0.7.0

- `.sail-worktree.json` は任意になりました。ファイルがなければ、`up`・`stop`・`rm` は `artisan` と compose ファイルがあるディレクトリで、compose ファイルとポート変数を実行のたびに検出します。ファイルがあるプロジェクトの動作は以前と同じです。
- `init` は compose ファイルの隣に `artisan` が必要になりました。compose ファイルしかないディレクトリ（`.devcontainer/` など）には書かなくなりました。"updated" と表示することがあり、既存のファイルを手で編集した内容は置き換わります。
- ポートの検出は、既定値が 1〜65535 のホスト側のポート指定（`'${APP_PORT:-80}:80'`）だけを対象にします。そのため `init` は、`DB_PORT=${DB_PORT:-3306}` のような `environment:` の項目を挙げなくなりました。
- ファイルがない場合、ポートはそのワークツリーでチェックアウトしているブランチの compose ファイルに従います。なくなった変数のポートは、次の `up` で解放されます。
- `up` は `.env` やレジストリに書く前に `vendor/bin/sail` を確認し、"created .env" は書いた後に表示します。
- メインワークツリーでは、設定のエラーより先に "cannot run in the main worktree" を出すようになりました。また、見つからないときのエラーは `init` の実行を勧めなくなりました。

### それ以前の版

- リポジトリのサブディレクトリにある Laravel プロジェクトに対応しました（[プロジェクトディレクトリ](#プロジェクトディレクトリ)を参照）。ワークツリーのルートにあるプロジェクトには影響しません。プロジェクトディレクトリ・プロジェクト名・ポートの割り当ては以前と同じです。
- `init` は、カレントディレクトリから上にたどって最初に見つかる compose ファイルの隣に `.sail-worktree.json` を書きます。以前は常にワークツリーのルートに書いていました。そのため、独自の compose ファイルを持つサブディレクトリ（`.devcontainer/` など）で実行すると、そこに書きます。
- `up`・`stop`・`rm` は、最も近い `.sail-worktree.json` を使います。独自の `.sail-worktree.json` がコミットされたディレクトリ（`vendor` と `node_modules` の外）はそれ自体がプロジェクトになり、独自の `.env` と `vendor/bin/sail` を使い、別のプロジェクト名になります。ルートにあるプロジェクトのコンテナはそのまま残り、そのディレクトリで実行した `rm` は、そのディレクトリ自身のプロジェクトだけを削除します（そのディレクトリに `up` が作った `.env` がないとき、または名前が一致しないときは拒否します）。
- `init` が compose ファイルを探すとき、存在するのに通常ファイルでない名前（`compose.yaml` という名前のディレクトリなど）は、受け入れずにエラーにするようになりました。`init` は、リンクや通常ファイルでない `.sail-worktree.json` を拒否します。
- `rm` は compose ファイルをプロジェクトディレクトリに対して検査するので、サブディレクトリのプロジェクトから、ワークツリーの別の場所にある compose ファイルへのリンクは拒否されます。
- `init` は作成したパスを引用符付きで表示し（`created "<パス>"`）、エラーメッセージの制御文字はエスケープして表示します。
- ワークツリーのパスはシンボリックリンクを解決した実パスになりました（例: macOS の `/tmp` → `/private/tmp`）。プロジェクト名にはそのパスのハッシュが入ります。古い版でシンボリックリンク経由のパスから `up` していた場合は名前が変わり、`up` は新しい名前を書いて旧コンテナ・ボリュームを残し、`rm` は `does not match`（英語のエラーメッセージ）で拒否します。旧プロジェクトは手で消す（`docker compose -p <旧名> down -v`）か、`.env` に旧名を戻してください。ただしポートは引き継がれます。ポートのレジストリは自動で移行され、シンボリックリンク経由のパスで記録されたエントリは次の `up` で実パスのエントリに統合されるので、そのワークツリーは以前のポートのままです（実パスに既にエントリがあればそちらを優先し、存在しないパスのエントリは触りません）。`rm` もそうした別名のエントリを実パスのエントリと一緒に解放しますが、`rm` が動くのは名前が一致したときだけです。
- ワークツリーの `.env` に既にある `SESSION_COOKIE` は次の `up` で上書きされるので、そのワークツリーのログインは一度切れます。
- `up` は、`.env` に `SANCTUM_STATEFUL_DOMAINS` があるとき、ワークツリーの `APP_URL` をそこに追加するようになりました（上の `up` を参照）。また `APP_URL` を書き換えるとき、IPv6 のホストの角括弧を保つようになりました（以前は `http://[::1]` が不正な `http://::1:<ポート>` になっていました）。
- `up` と `rm` は、`.env` がシンボリックリンク・ハードリンクのときエラーになります。また `up` は `.env` に `COMPOSE_FILE`・`COMPOSE_ENV_FILES`・`SAIL_FILES` の行があるとき（メインワークツリーの `.env` からコピーされたものを含む）、`rm` はさらに `COMPOSE_PROFILES` の行があるときもエラーにします（`up` は `COMPOSE_PROFILES` を許します）。リンクを実ファイルに置き換えるか、その行を消してください。`stop` はこれらを拒否せず、警告だけ出します。
